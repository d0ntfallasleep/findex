# Що змінилося при паралельній збірці

У моєму корпусі 27 файлів. Для кожного треба прочитати текст, знайти токени, збільшити лічильники і записати позиції. Очікування читання можна перекрити іншою роботою. Але після читання значна частина часу йде на цикли та зміни словників у Python. У звичайному CPython GIL дозволяє лише одному потоку одного інтерпретатора виконувати Python-байткод у кожен момент. Чотири потоки тут дали 0,0732 с проти 0,0602 с послідовно. Для малих локальних файлів можливість читати одночасно не окупила керування потоками. Дослід вимірює весь конвеєр і не визначає точну частку часу диска.

Процеси мають окремі інтерпретатори. Перехід з одного процесу пулу на чотири скоротив wall з 0,1955 до 0,1316 с. Але послідовна збірка в основному процесі все одно завершилася більш ніж удвічі швидше за чотири процеси. При spawn кожен воркер запускає інтерпретатор та імпортує модулі. На вхід достатньо передати шляхи і початковий номер документа. Назад через pickle їде значно більше даних: метадані, частоти і списки позицій. Для чотирьох процесів загальний CPU склав 0,3838 с при wall 0,1316 с. Ядра справді працювали одночасно, але сумарної роботи побільшало. RSS батька 33,15 МіБ не включає пам’ять чотирьох дочірніх інтерпретаторів.

За законом Амдала, якщо послідовна частка роботи дорівнює f, ідеальне прискорення обмежене 1/(f+(1-f)/N). У послідовному замірі merge забрав 0,0066 с із 0,0602 с, тобто приблизно 11%. Навіть якщо уявити миттєву побудову частин, за незмінної вартості лише цього merge межа близько 9×. Реальний merge для чотирьох процесів зайняв 0,0100 с. На малому корпусі додатковий запуск та обмін даними відтісняють результат далеко від цієї ідеалізованої межі.

У 3.13t два потоки дали 0,0864 с проти 0,0880 с у власному serial. Різниця близько 2% на трьох повторах занадто мала для висновку про стійкий виграш. На дев’яти потоках час виріс до 0,1046 с. Вимкнення GIL дозволило виконувати цикли паралельно, але залишилися внутрішня синхронізація об’єктів, виділення пам’яті, нерівна довжина розділів і послідовний merge. Абсолютний час найкращого потокового запуску 3.13t також більший за звичайний serial. Тому для цього корпусу лишив типовим serial.

Спільний вираз counts[word] += 1 потребує читання, обчислення і запису. Якщо два воркери прочитають одне старе значення, можна втратити одне збільшення. GIL не є гарантією атомарності такого інваріанта. Тут кожен воркер володіє власним Counter та списками, а готові результати об’єднує один потік. У тестах перевіряю рівність індексу та байтів файлів, включно з позиціями й пропущеним пошкодженим текстом. Гонки лічильників у цьому досліді не спостерігав.
